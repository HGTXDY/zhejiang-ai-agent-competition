# 模块分工与并行开发边界

## 1. 角色关系

- HGTXDY 与 cbiiro97977 具有对等的开发权限和 Review 权限。
- HGTXDY 负责维护任务池、确定实施顺序并向 cbiiro97977 派发任务。
- Issue 负责人拥有该模块的实现主责；公共契约变更必须由另一位研发交叉 Review。
- 双方不直接向 `main` 推送，所有变更均通过 Issue、独立分支、CI 和 PR。

## 2. 当前研发范围

当前两人负责：

- 菜谱结构化数据与标注评测；
- 领域模型、Schema 和 API 契约；
- 后端服务、输入校验和设备能力模型；
- CP-SAT 初始调度与多目标优化；
- 执行状态、事件模型和最小扰动重排；
- 自动测试、性能、Docker 和产品交付工程；
- 产品前端主流程、排程甘特图、执行页面、事件上报和重排差异展示。

不在当前两人分工内：

- PPT、录屏、路演文案和展示包装；
- 外部成员不得修改产品功能或开发产品交互。

## 3. 并行开发规则

1. 公共契约放在 `contracts/v1/`，下游只依赖已合并的版本化 Schema 和样例；
2. 前后端、数据和算法模块可以使用契约样例或 fixture 开发，不等待真实上游实现；
3. 每个 Issue 明确可写目录、输入、输出和验收命令，避免两个分支修改同一组文件；
4. 公共字段变更先走契约 PR，不在实现 PR 中顺手修改；
5. 集成发生在契约版本或里程碑边界，不通过共享未合并分支耦合开发。

## 5. Review 与合并规则

- cbiiro97977 的 PR 由 HGTXDY Review；
- HGTXDY 的 PR 由 cbiiro97977 Review；
- Reviewer 对正确性、测试、兼容性和可维护性具有同等阻塞权；
- CI 未通过或存在未解决的阻塞意见时不得合并；
- 统一使用 Squash Merge，合并后删除分支。
