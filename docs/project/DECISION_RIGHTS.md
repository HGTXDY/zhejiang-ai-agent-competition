# 决策权、任务分配与变更流程

## 1. 协作原则

HGTXDY 与 cbiiro97977 在仓库中拥有对等的开发、提交、Review 和技术提议权。双方均可审查对方分支、提出阻塞意见，并对自己批准的代码质量负责。

唯一的角色差异是：**HGTXDY 维护产品任务池、确定当前优先级并向 cbiiro97977 派发任务**。任务分配不代表代码权限、评审权或专业地位不对等。

## 2. 工作方式

| 事项 | 规则 |
|---|---|
| 产品范围与优先级 | HGTXDY 根据比赛目标维护并派发任务；范围变化必须记录到 Issue |
| 技术方案 | 模块实现者可提出方案；涉及公共契约时必须经另一位研发 Review |
| Schema 与 API | 通过版本化契约和 PR 冻结，任何一方不得在自己的分支中静默破坏兼容性 |
| 模块实现 | Issue 被派发后，由负责人自主实现并对验收结果负责 |
| Code Review | 双向交叉 Review；HGTXDY 的 PR 由 cbiiro97977 审，cbiiro97977 的 PR 由 HGTXDY 审 |
| 合并 | 至少获得另一位研发批准且 CI 通过后，使用 Squash Merge |
| 风险处理 | 任何一方均可提出阻塞；不得绕过 Review、测试或已冻结契约 |

## 3. 需求与公共契约变更

1. 创建或更新 GitHub Issue，说明原因、影响模块、兼容性和验收变化；
2. 如影响公共 Schema/API，先修改版本化契约、样例和契约测试；
3. 另一位研发完成 Review，争议在 Issue 或 ADR 中留下结论；
4. 契约 PR 合并后，下游模块再分别适配；
5. HGTXDY 更新任务池和派发顺序。

## 4. 当前团队边界

当前两位研发承担完整产品研发，包括数据、解析、校验、调度算法、动态重排、API、产品前端和全部产品内交互。

产品内交互包括但不限于：菜谱配置、设备配置、调度结果、甘特图、执行状态、倒计时、完成/延迟/加菜/设备异常操作、重排差异和通知。

以下工作由其他成员承担：

- 基于我们完成的可运行产品编写 PPT；
- 基于我们完成的可运行产品录制视频；
- 路演文案、展示包装和其他演示材料。

外部成员不修改产品功能，不开发产品交互。产品研发侧向其提供可运行成品、使用说明和必要的演示数据。
